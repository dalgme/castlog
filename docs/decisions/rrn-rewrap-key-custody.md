# 주민등록번호 복호화 — 키 보관·재래핑 운영 설계 (제안)

작성: 2026-08-16 · 상태: **제안(승인 대기)** · 관련: CLAUDE.md §4·§5·§11-4,
docs/decisions/rrn-phase2-secure-subsystem.md

## 0. 배경 — 검증에서 발견한 공백

수집→복호화 경로를 코드로 검증한 결과, **복호화용 개인키의 소재가 정의되어
있지 않다.**

- 현재 수집(`app/(expert)/expert/profile/rrn-actions.ts`)은 **서비스 공개키**
  (`rrn_service_keys.public_key_jwk`, 테넌트 무관)로 봉투를 암호화한다. — "주민번호는
  기업과 무관하게 먼저 입력"이라는 확정 요구(§4)에 맞춘 올바른 방향.
- 그러나 **서비스 *개인*키는 DB·코드 어디에도 없다.** 즉 지금 상태로는 수집된
  봉투를 풀 수 있는 주체가 존재하지 않는다.
- 계약 시점 재래핑(`tax_project_grants`)은 빈 테이블 + 주석 자리표시자일 뿐 미구현.

### 근본 긴장
1. 수집은 **계약 이전**에 일어난다(테넌트·조회 비밀번호가 아직 없음).
2. §11-4: **에스크로·마스터 복호화 키 금지.** 조회 비밀번호 없이 복호화되는 키를
   두면 안 된다.
3. → "서비스 개인키를 어딘가에 영구 보관"하면 그것이 **모든 사전수집 주민번호를
   조회 비밀번호 없이 풀 수 있는 마스터키**가 되어 §11-4 위반이다.

## 1. 후보 비교

| | A. 서비스 개인키 영구 보관 | **B. 전문가 보유 키 + 승인 시 재래핑(권장)** | C. 계약 시점에만 수집 |
|---|---|---|---|
| 사전 입력(§4) | 가능 | 가능 | **불가(요구 위반)** |
| 마스터키 없음(§11-4) | **위반**(서비스키가 사실상 마스터키) | 준수(플랫폼이 풀 수 있는 키 없음) | 준수 |
| 복호화 주체 | 분리 서비스 | 조회 비밀번호 보유자(회계·대표)만 | 동left |
| 재래핑 시점 개인키 | 서비스가 상시 보유 | **전문가 브라우저에서 그 순간만**(비영구) | 불필요 |
| 전문가 개입 | 불필요 | 섭외 **승인 시**(어차피 전문가가 하는 행위) | 불필요 |
| 서버 복호화 능력 | 있음(분리 서비스) | **없음**(전 과정 브라우저) | 없음 |

## 2. 권장안 — B: 전문가 보유 키 + 승인 시 재래핑 (전 과정 브라우저 암호)

수집 화면이 이미 브라우저 전용 봉투 암호(`lib/crypto/rrn-envelope.ts`)를 쓰는 것과
동일한 원칙을 복호화·재래핑까지 확장한다. **서버·플랫폼은 어떤 단계에서도 평문·
복호화 키를 보지 않는다.**

### 2.1 수집 (변경: 서비스키 → 전문가 키)
- 전문가 브라우저에서 **전문가 키페어** 생성.
  - 공개키: 메인 DB(전문가 소유 레코드).
  - 개인키: **전문가 보관 비밀번호(passphrase)**에서 유도한 키(Argon2id)로 래핑해
    저장. passphrase는 어디에도 저장 안 함.
- 주민번호 → DEK로 앞/뒤 분할 암호화, DEK를 **전문가 공개키**로 래핑.
  앞조각+wrapped_dek→메인, 뒷조각→저장소 B. (테넌트 무관, 계약 전 가능)

### 2.2 재래핑 (섭외 **승인** 시 = 전문가가 온라인인 순간)
- 전문가가 `/e` 동의/승인 화면에서 수락할 때, 브라우저에서:
  passphrase 입력 → 전문가 개인키 언래핑 → **DEK만** 언래핑(평문 주민번호는 건드리지
  않음) → 그 계약의 **테넌트 공개키**로 DEK 재래핑 → `tax_project_grants`에 저장.
- 서버는 재래핑 결과(암호문)만 받는다. 개인키·DEK 평문은 브라우저 메모리에서만.
- 테넌트 공개키/개인키는 기존 `tenant_rrn_keys`(개인키는 그 테넌트 **조회 비밀번호**로
  래핑) 사용.

### 2.3 조회(복호화) — 회계담당·대표
- 조회 화면에서 **조회 비밀번호** 입력 → 테넌트 개인키 언래핑 → `tax_project_grants`의
  DEK 언래핑 → 앞조각(메인)+뒷조각(저장소 B, 인증 릴레이 경유) 결합 복호화 →
  지급명세서 생성/마스킹·워터마크 표시. **브라우저에서만**, 평문은 생성 후 폐기.
- 플랫폼관리자(넥스트랩)는 조회 비밀번호가 없으므로 구조적으로 불가(§5).

### 2.4 "분리 복호화 서비스"의 실제 역할 = 최소 권한 인증 릴레이
- 복호화를 서버가 하지 않으므로, 분리 서비스(Edge Function)는 **저장소 B의 뒷조각
  암호문을 인가된 조회 세션에만 전달**하고, **한도·잠금·허니토큰·로그·전문가 통지**를
  강제하는 게이트 역할만 한다. 평문·키를 절대 보지 않는다.
- 1요청 = 1건, 시간당 상한/자동 잠금, 승인된 지급 결재 연결 필수(§5) 모두 이 게이트에서.

## 3. service_role 키는 어디서 뽑나 (질문 답)

Edge Function은 배포된 **한 프로젝트**의 service_role만 자동 주입받는다. 다른 프로젝트
접근은 그 프로젝트의 service_role을 secret으로 넣어야 한다.

- 릴레이 함수를 **메인 프로젝트**에 배포(설계문서 스캐폴드 위치) → 저장소 B 뒷조각을
  읽어야 하므로 **`castlog-rrn-store-b` 프로젝트의 service_role**을 함수 secret으로
  등록. (이미 Vercel에 넣으신 `RRN_STORE_B_SERVICE_KEY`와 동일 값)
- 릴레이 함수를 **`castlog-rrn-store-b` 프로젝트**에 배포 → 저장소 B는 자동 주입,
  대신 **메인 프로젝트 service_role**을 secret으로 등록.

권장: **저장소 B 프로젝트에 배포**(격리 강화 — 메인 프로젝트에 복호화 관련 코드/키를
두지 않음). 이 경우 뽑을 키는 저장소 B가 아니라 **메인 프로젝트 service_role**이다.
단, 릴레이는 뒷조각 암호문만 다루므로 메인 접근 범위를 최소화(뒷조각 전달·게이트
기록에 필요한 테이블로 한정)한다.

## 4. 운영 안전장치 (공통)
- 조회 비밀번호·passphrase는 **어디에도 저장 금지**. 분실 시 복구 불가(에스크로 없음) —
  회전 절차는 재키생성+재래핑으로 처리.
- 모든 조회·재래핑은 `tax_access_logs` 기록 + 전문가 즉시 통지(알림 뱃지).
- 시간당 상한 초과 자동 잠금, 허니토큰 복호화 시도 시 전체 잠금.
- 주민번호 조회 권한은 대결·위임 대상에서 제외(코드 강제, `rrn-access.ts`).

## 5. 결정 필요 사항
1. 권장안 B(전문가 보유 키 + 승인 시 브라우저 재래핑) 채택 여부.
   - 채택 시: 현재 서비스키 수집분을 전문가키 모델로 이전(초기 데이터 소량, 재수집 또는
     마이그레이션). 전문가 passphrase UX(설정·승인 시 입력) 추가.
2. 릴레이 함수 배포 위치(저장소 B 권장) → 그에 맞는 service_role secret 등록.
3. 조회 비밀번호/ passphrase 회전·2차 인증 정책.
