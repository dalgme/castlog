# 주민등록번호(RRN) Phase 2 보안 서브시스템 설계 (2026-08-15)

CLAUDE.md §5(민감정보 처리)·§11(Hard NO #3·#4)·설계문서 4.4·8.7절을 근거로,
주민등록번호의 **수집·저장·조회·파기** 전 과정을 설계한다. 이 문서는 구현 착수
전 판정 기록이며, 각 구현 단계는 §14-8(단계 승인 게이트)에 따라 승인 후 진행한다.

> 이 문서가 정의하기 전까지, 메인 앱은 주민번호를 **저장하지도 복호화하지도
> 않는다**(이미 적용 완료 — `20260815000001`의 `tax_access_logs`는 SELECT 전용,
> INSERT 정책 없음). 본 설계의 실수집·복호화 능력은 **분리된 전담 서비스**에만
> 존재한다.

---

## 1. 목적·법적 근거

- **목적**: 소득세법상 원천징수·지급명세서 제출 의무 이행을 위해, 지급 대상
  전문가의 주민번호를 **최소한으로, 필요 시점에만** 처리한다.
- **근거는 동의가 아니라 법령**(소득세법). 화면 문구는 "동의합니다"가 아니라
  "확인합니다"(고지 확인). 별도 동의 항목을 만들지 않는다.
- **기업은 번호를 보유하지 않는다.** 필요 시점에 조회만 한다.

## 2. 불변 원칙 (Hard NO 재확인 — 위반 시 즉시 보안 결함)

1. 평문 주민번호를 **DB·로그·캐시·APM·클라이언트 상태**에 저장 금지.
2. **메인 앱(Next.js)에 복호화 능력을 두지 않는다.** 복호화는 분리 서비스 전용.
3. **에스크로·마스터 복호화 키를 만들지 않는다.** 조회 비밀번호는 어디에도 저장 안 함.
4. **일괄 조회 API 금지** — 1요청 = 1건. 상시 조회 화면 없음.
5. 승인된 **지급 결재건에 연결되지 않은** 조회 요청은 거부.
6. **플랫폼관리자(넥스트랩)도 조회 불가.** 대결·위임 대상에서 코드로 제외.
7. 사업자 청구 전문가는 **수집하지 않는다**(세금계산서 — 주민번호 불필요).

## 3. 위협 모델 (방어 대상)

| 위협 | 방어 |
|---|---|
| 메인 DB 단독 유출 | 앞/뒤 **분할 저장**(별도 저장소·자격증명) — 한쪽만으론 복원 불가 |
| 메인 앱 서버 침해 | 앱에 복호화 키·능력 없음 — 분리 서비스만 복호화 |
| 내부자(개발자·운영자) | 조회 비밀번호 미저장, tax_access_grants 지정자만, 플랫폼관리자 차단 |
| 대량 유출(스크래핑) | 1요청=1건, 시간당 상한, 초과 시 자동 잠금 + 경보, 일괄 API 부재 |
| 로그·APM 유입 | 파이프라인 **최전단 마스킹 필터**, 평문 로깅 경로 원천 차단 |
| 미끼 탐지 회피 | **허니토큰** 레코드 — 복호화 시도 시 즉시 전체 잠금 |
| 권한 상승(대결·위임) | 주민번호 권한은 대결·위임에서 코드로 제외 |

## 4. 아키텍처 (3개 신뢰 경계)

```
[메인 앱 Next.js]            [분리 복호화 서비스]         [분할 저장소 B]
 - 조회 요청 생성/검증         - 유일한 복호화 주체          - 주민번호 "뒷조각"
 - 지급결재 연결 확인          - Argon2id 키 유도            - 별도 자격증명·별도 키
 - grants/limit/lock 판정      - 지급명세서 파일 생성        - 메인 DB와 물리 분리
 - 마스킹·워터마크·감사        - 앞/뒤 조각 결합→복호화
 - 복호화 능력 없음 ✗          - 평문 미저장(생성 후 폐기)
        │                            │  ▲
        └── 서명된 1건 요청 ────────►│  │ 뒷조각 fetch (mTLS/별도 credential)
                                     ▼  │
                             [분할 저장소 A: 메인 DB]
                              - 주민번호 "앞조각" + 래핑된 DEK
```

- **분리 복호화 서비스**: 별도 배포 단위(별도 리포/서비스, 최소 권한). 메인 앱은
  이 서비스에 **1건 단위 서명 요청**만 보낸다. 서비스는 파일(지급명세서)을 생성해
  돌려주고 평문은 메모리에서만 다루며 즉시 폐기한다.
- **분할 저장**: 주민번호를 앞/뒤로 나눠 **서로 다른 저장소·자격증명·키**에 보관.
  메인 DB(A)는 앞조각만, 저장소 B는 뒷조각만.

## 5. 키 계층 (봉인 순서)

```
평문 RRN
  └─ 레코드 DEK(AES-256-GCM, 레코드마다 새로 생성)로 암호화
       └─ DEK를 테넌트 키로 래핑
            └─ 테넌트 키를 "조회 비밀번호에서 유도한 키(Argon2id)"로 래핑
                 → tax_project_grants 에 저장 (프로젝트·기업 권한자용으로만)
```

- **조회 비밀번호**: 권한자(회계담당·대표)가 조회 시점에 입력. **어디에도 저장하지
  않는다.** 유도 키(Argon2id, 고유 salt·충분한 파라미터)로 테넌트 키를 언래핑.
- 권한 발생 시점 = **전문가의 섭외 승인(계약 성립)**. 이때 해당 프로젝트·해당 기업
  권한자용으로만 DEK가 래핑된다(`tax_project_grants`).
- **파기**: 지급 완료 + 법정 보존기간 경과 시 래핑을 자동 폐기(§14-4 예외 — 파기 우선).

## 6. 데이터 모델 (신규/확장)

| 테이블 | 저장소 | 내용 | 접근 |
|---|---|---|---|
| `rrn_fragments_front` | 메인 DB(A) | 앞조각 암호문 + 래핑된 DEK + salt·nonce | 서비스만(RLS deny-all, service_role) |
| `rrn_fragments_back` | **저장소 B** | 뒷조각 암호문 | 복호화 서비스 전용 자격증명 |
| `tax_project_grants` | 메인 DB | (기존, 현재 빈 테이블) 프로젝트·기업별 DEK 래핑 | 서비스만 |
| `tax_access_grants` | 메인 DB | 조회 지정자(회계담당·대표) — 대결·위임 제외 | org_admin 관리 |
| `tax_access_requests` | 메인 DB | 지급결재 연결 1건 조회 요청(사유·상태·재인증) | 권한자 생성, 서비스 소비 |
| `tax_access_logs` | 메인 DB | **(구현 완료)** 조회 이력 — 전문가 본인 공개 | expert SELECT |
| `tax_rate_limits` | 메인 DB | 사용자·테넌트별 시간당 복호화 카운트/잠금 | 서비스만 |
| `tax_honeytokens` | 메인 DB | 미끼 레코드 — 복호화 시도 감지 | 서비스만 |

## 7. 수집 흐름 (Collection)

1. **시점**: 지급 확정 단계에서만 수집(사전 수집 금지). 사업자 청구 전문가는 제외.
2. **입력 주체**: 전문가 본인이 전용 보안 입력 화면에서 1회 입력 → 클라이언트에서
   즉시 분할·암호화되어 전송(평문이 서버 폼 로그에 남지 않도록 처리).
3. **항목별 정책 분리**(하나로 묶지 않음):
   - 이력서 = 계약기간 내 자유 열람(로그만)
   - 통장사본 = 지급 단계 열람(전건 로그) — *계좌번호 텍스트는 이미 별도 암호화 구현*
   - **주민번호 = 프로젝트당 2회 한도 + 재인증 + 전문가 즉시 알림**

## 8. 조회 흐름 (Access) — 기본은 "파일 자동생성"

1. **기본 경로**: 화면 단건 조회가 아니라 **지급명세서 파일 자동생성**. 파일 생성도
   조회로 간주해 로그·통지. 화면 단건 조회는 **예외 처리용**.
2. 조회 요청은 반드시 **승인된 지급 결재건에 연결**(`tax_access_requests`). 연결
   없으면 거부. 상시 조회 화면 없음.
3. **1요청 = 1건.** 일괄 API 없음.
4. **재인증**(조회 비밀번호 + 2차 수단) 후에만 복호화 서비스 호출.
5. **한도**: 프로젝트당 2회. 초과는 **차단하지 않음** — 사유 기재 + 대표 승인 +
   전문가 통지로 처리(세무조사·경정청구 등 정당 초과 대비).
6. **시간당 복호화 상한**(사용자·테넌트별) 강제. 초과 시 **자동 잠금 + 경보**.
7. **모든 조회** → `tax_access_logs` 기록 + **전문가 본인에게 즉시 알림**(이미 이력
   공개 화면 구현). 화면 노출 시 **조회자·시각 워터마크**, 일정 시간 후 자동 재마스킹.
8. **허니토큰** 복호화 시도 감지 시 **즉시 전체 잠금**.

## 9. 권한 (Authorization)

- 조회 권한: `tax_access_grants` 지정자(**회계담당자·대표자**)만.
- **플랫폼관리자(넥스트랩)도 조회 불가.** 대결·위임 대상에서 **코드로 강제 제외**.
- 권한은 프로젝트·기업 범위로 한정(계약 성립 프로젝트에 한함).

## 10. 로깅·마스킹·파기

- **마스킹 필터를 로그 파이프라인 최전단**에 배치(평문 RRN 패턴 차단).
- 평문을 DB·로그·캐시·APM·클라이언트 상태에 저장 금지.
- 지급 완료 + 법정 보존기간(세무 5년 기준, 확정 후 조정) 경과 시 **자동 파기**.

## 11. 단계별 구현 계획 (승인 게이트마다 보고)

| 단계 | 범위 | 산출물 | 신뢰 경계 |
|---|---|---|---|
| **2.1** | 데이터 모델·RLS·감사 골격 | grants/requests/limit/honeytoken 테이블 + deny-all RLS, 마스킹 로그 필터 | 메인 앱(복호화 능력 없음) |
| **2.2** | 조회 요청·권한·한도 로직 | 지급결재 연결 검증, tax_access_grants 관리 UI, 한도·잠금·경보 | 메인 앱 |
| **2.3** | 분리 복호화 서비스 스캐폴드 | 별도 서비스(1건 요청→파일), Argon2id 유도, 앞/뒤 조각 결합 | 분리 서비스 |
| **2.4** | 분할 저장소 B + 수집 흐름 | 저장소 B 프로비저닝(별도 자격증명), 전문가 보안 입력 화면 | 저장소 B |
| **2.5** | 지급명세서 자동생성·통지·워터마크·재마스킹 | 파일 생성 기본 경로, 전문가 알림 연동 | 분리 서비스 + 메인 앱 |
| **2.6** | 허니토큰·자동 파기·침해 대응 | 미끼 감지 전체 잠금, 보존기간 경과 파기 배치 | 전체 |

각 단계는 빌드·실동작 확인(§14-7) 후 보고하고 승인받아 다음 단계로 진행한다.

## 12. 미결 결정사항 (착수 전 확인 필요)

1. **분리 복호화 서비스 배포 형태**: 별도 Vercel 프로젝트 / 별도 컨테이너(예: Fly·Cloud
   Run, 서울 리전) / Supabase Edge Function(격리 강화) 중 택. — 인프라·비용 결정.
2. **분할 저장소 B**: 별도 Supabase 프로젝트(서울) vs 별도 오브젝트 스토리지. 별도
   자격증명·별도 키 필수.
3. **테넌트 키·조회 비밀번호 관리 UX**: 조회 비밀번호 최초 설정/회전 절차, 2차 인증
   수단(문자 OTP 재사용 vs 별도).
4. **KMS/키 보관**: 테넌트 키 봉인에 사용할 상위 키의 보관처(환경변수 vs 관리형 KMS).
5. **법정 보존기간 확정**: 세무사 확인 후 파기 주기 확정(현재 초안 5년).

> 위 5개는 인프라·법무 결정이 섞여 있어, **2.1(메인 앱 내 안전 골격)**은 결정과
> 무관하게 먼저 진행 가능하고, **2.3~2.4(분리 서비스·저장소 B)**는 1·2·4번 결정이
> 선행되어야 한다.

## 13. 구현 진행 로그 (승인·결정 반영)

### 확정된 인프라 (사용자 승인)
- **분리 복호화 서비스**: Supabase Edge Function `rrn-decrypt` (메인 프로젝트, 미배포 스캐폴드)
- **저장소 B**: 별도 Supabase 프로젝트 **생성 완료** (월 $10 승인)
  - project: `castlog-rrn-store-b` / id `jdtgbtigpjvxxvrdcbrg` / 서울(ap-northeast-2)
  - URL: `https://jdtgbtigpjvxxvrdcbrg.supabase.co`
  - 스키마 적용됨: `rrn_fragments_back`(deny-all)
- **상위 키 보관**: 초기 환경변수 → 이후 관리형 KMS 전환

### 확정된 암호 설계 — 비대칭 봉투(수집 시 조회비밀번호 불필요)
수집 시점에는 조회 비밀번호가 없으므로(조회 비밀번호는 회계담당·대표의 것),
**테넌트별 비대칭 키페어**로 봉투 암호화한다:
- **공개키**(메인 DB, 비밀 아님): 수집 시 레코드 DEK를 래핑한다.
- **개인키**: 테넌트 조회 비밀번호에서 유도한 키(Argon2id)로 래핑해 보관. 조회
  비밀번호는 저장하지 않는다.
- **수집(전문가)**: DEK 생성 → RRN 앞/뒤 분할·AES-256-GCM 암호화 → DEK를 테넌트
  공개키로 래핑 → 앞조각·wrapped_dek(메인) + 뒷조각(저장소 B) 저장. (조회 비밀번호 불필요)
- **복호화(회계담당·대표, rrn-decrypt 서비스)**: 조회 비밀번호 → Argon2id → 개인키
  언래핑 → DEK 언래핑 → 앞+뒤 결합 복호화 → 지급명세서 생성. 평문은 메모리에서만.

### 남은 작업 (2.4 — 순서)
1. **테넌트 RRN 키페어 · 조회 비밀번호 설정** 플로우(회계담당·대표): 키페어 생성,
   개인키를 조회 비밀번호로 래핑 저장(`tenant_rrn_keys` 신규).
2. **전문가 수집 입력 화면**: 클라이언트 암호화(공개키 봉투) → 앞/뒤 분할 전송 →
   메인/저장소 B 저장. 평문은 서버·로그에 남기지 않음(마스킹 필터 적용).
3. **rrn-decrypt 활성화**: 저장소 B service_role 시크릿 설정 + 배포 + 개인키 언래핑·
   파일 생성 구현.
4. 허니토큰·자동 파기(2.6).

> 운영 메모: `rrn-decrypt` 배포 시 저장소 B의 **service_role 키**를 Edge Function
> 시크릿(`RRN_STORE_B_SERVICE_KEY`)으로 설정해야 한다. 이 키는 MCP로 노출되지 않아
> 대시보드(castlog-rrn-store-b → Project Settings → API)에서 복사해 등록한다.
