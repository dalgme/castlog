# 테넌트 데이터 자가보관(백업) 및 네이버웍스 연동 판정 기록 (2026-08-09)

회사(테넌트)별 데이터 격리·자가보관 요구에 대한 아키텍처 선택과,
네이버웍스(NAVER WORKS) 연동 가능성 검토 판정. 향후 설계 문서/단계
계획에 반영한다.

---

## 1. 배경 — 요구사항

- 각 회사가 "자사 데이터를 자사가 통제하는 곳에 저장/보유"하고 싶다.
- 단, **전문가는 회사 간 재사용**되어야 한다(전문가 신원 모델, CLAUDE.md 4장 불변).

## 2. 검토한 3개 모델

| 모델 | 내용 | 운영 부담 | 판정 |
|---|---|---|---|
| A. 공유 DB + RLS (현재) | 한 Supabase에 전 회사, `tenant_id`로 논리 격리 | 낮음 | 기본 유지 |
| B. 회사별 DB 분리 | 회사마다 별도 Supabase 프로젝트에서 **작동** | 높음(N배) | **제외** |
| C+. 공유 DB + 회사별 백업 자가보관 (보정판) | 라이브는 공유, 회사 데이터 사본을 회사 소유 저장소로 정기 전달 | 낮음 | **채택** |

### B안 제외 사유
- 마이그레이션·모니터링·백업이 회사 수만큼 곱해짐(운영 N배).
- 핵심 연동(experts↔operations↔approvals)이 DB JOIN/FK에서 앱 페더레이션으로
  내려가 유지보수·보안 부담 급증.
- **개발기간·기회비용 과다** — 현 단계에서 수용 불가(사용자 판정).
- 강한 규제(공공·대기업 물리격리 의무) 요구가 실제로 발생하면 최상위 옵션으로
  재검토(보류, 폐기 아님).

### C+안 채택 근거
- 현 스키마가 이미 전역(전문가 소유)/테넌트(`tenant_id`) 경계로 분리되어 있어
  절단면이 존재 — 사본 추출이 깔끔하다.
- 운영 방식(업그레이드·연동·모니터링)은 지금 그대로. 추가 부담 최소.
- "회사가 통제하는 최신 사본 보유"라는 실제 요구를 저비용으로 충족.
- 기존 엑셀 내보내기 인프라(단계 13) 재활용 가능.

## 3. C+ 설계 원칙 (확정)

### 3.1 민감정보 처리 (최우선 — CLAUDE.md 5장 준수)
- **주민등록번호: 백업에서 완전 제외** (암호문조차 미포함 — 기업 비보유 원칙).
- **신분증·통장 사본·서명 원본: 원본 파일 제외**, 존재·열람권한 **메타데이터만** 포함.
- **지급명세서: 마스킹본을 백업에 포함**한다.
  - 성명·지급액·원천징수세액·지급일·프로젝트 등 업무 항목은 전부 포함.
  - 주민번호·계좌는 마스킹(`******`). 원천 민감정보를 드러내지 않는다.
  - 마스킹본 생성은 주민번호를 노출하지 않으므로 5장의 "조회 경로·전문가 통지"를
    **트리거하지 않는다**(설계 이점). 평문 주민번호 복호화 없이 생성.
  - 주민번호 평문 포함 **원본** 지급명세서는 법정 제출용 별도 통제 경로로만.
- 일반 업무 데이터(프로젝트·결재·섭외이력·지급내역·발송로그·감사로그 등): 전부 포함.
- 전문가: 회사가 연결된 전문가의 **비민감 프로필 스냅샷만** 포함(원래 열람 가능 범위).

### 3.2 목적지(백업 도착지) — 지원 우선순위
1. **① 오브젝트 스토리지(회사 소유 파일 보관함, S3 호환)** — 우선 지원.
2. **④ 네이버웍스 Drive** — 우선 지원(웍스 사용 회사 대상, 아래 5절 연동과 연계).
3. **② 회사 DB(Postgres 등) 직접 적재** — **추후 과제로 기록**(사용자 지정).
   회사별 DB 종류·접속권한·스키마 매핑 부담이 있어 후순위.
4. ③ SFTP — 수요 발생 시.

### 3.3 전달·무결성·안전장치
- 포맷: `열람용`(엑셀/CSV) + `적재용`(JSON/SQL) 두 프로파일.
- 회사 통제 키로 패키지 암호화(전송 중·보관 시).
- 매 백업에 **매니페스트**(테이블·행수·시점·파일별 체크섬·스키마 버전) 동봉 →
  회사가 완전성 검증. 문서화된 복원 절차 제공(더미 백업 금지, APDF 7).
- 시점 일관성 스냅샷(참조 무결성 유지), 참조 전문가 프로필 스냅샷 동봉(끊긴 참조 방지).
- 백업 기능 활성화·목적지 변경은 **위험 작업** → 2단계 확인 + 권한 분리(APDF 3).
- 모든 반출 실행 `audit_logs` 기록 + `tenant_usage_metrics` 계측. 실패 시 재시도·경보.
- 약관/DPA: 사본 수령 후 보관 책임은 회사에 있음(책임 경계 명시).

### 3.4 신규 테이블(구현 시 — 전부 tenant_id + RLS)
- `tenant_backup_configs` — 목적지 유형·암호화 자격증명·주기·포맷·포함범위·공개키·활성여부·승인상태
  (`tenant_sms_configs`와 동일 패턴).
- `tenant_backup_runs` — 실행 이력(시작·종료·상태·매니페스트·행수·용량·체크섬·오류).

### 3.5 단계적 도입
- MVP: 온디맨드 + 정기 전체 스냅샷(민감정보 제외), 암호화 JSON+SQL → 오브젝트 스토리지, 매니페스트·감사로그.
- 2단계: 증분(델타), 네이버웍스 Drive 어댑터, 포함범위 세부선택.
- 3단계(선택): 준실시간(논리복제/CDC) — 최상위 고객 요구 시.

## 4. C+ 한계 (오해 방지)
- 실시간 물리 격리가 아님(라이브는 공유 DB, 논리격리/RLS 유지). 사본은 시점 스냅샷.
- 사본은 읽기·적재용 아카이브. 그 위에서 CASTLOG가 작동하지 않는다(그건 B안).
- 원천 민감정보(주민번호 등)는 사본에 없다.

## 5. 네이버웍스(NAVER WORKS) 연동 검토

> ⚠️ 검증 한계: 이 환경의 네트워크 정책이 worksmobile.com·ncloud-docs 계열
> 도메인 egress를 차단하여 **공식 문서를 직접 열람하지 못했다.** 아래는 웹 검색
> 스니펫·보도자료·개발자 블로그 기반 정리이며, **구현 착수 전 공식 개발자
> 문서로 스코프·요금제(에디션)·국내(NAVER WORKS) 제공 여부를 재확인**해야 한다.

### 5.1 핵심 발견 — 연동 자유도는 2층 구조
1. **기본(대다수 예상대로): 아웃바운드 REST API + 인증**
   - Bot / Directory(조직도) / Drive / Calendar / Mail / Board 등 REST API 2.0.
   - OAuth 2.0(사용자 승인) + Service Account(JWT, 무승인 접근).
   - SSO/로그인 연동(웍스 계정으로 외부 서비스 로그인, 또는 회사 IdP로 웍스 로그인 SP).
   - → "API를 열어 타서비스와 연결"하는 통상 모델. 사용자의 직관과 일치.
2. **추가(사용자가 의심한 부분): WOFF (WORKS Front-end Framework)**
   - 2023년 정식 제공. **개발자가 만든 웹앱을 네이버웍스 클라이언트 "안에서"
     미니앱으로 실행**시키는 프레임워크(LINE의 LIFF에 대응).
   - 채팅/메뉴에서 바로 실행, 웍스 로그인 컨텍스트 유지, JS SDK(예: `woff.openWindow()`).
   - 모바일에서 외부 브라우저 설정과 무관하게 **웍스 앱 내부에서 구동**.
   - 단, "웍스 내부 소스에 코드를 심는" 것이 아니라 **내가 호스팅하는 웹앱을 웍스가
     품어 실행**하는 방식(웹앱 + SDK). 자유도는 이 수준.

### 5.2 CASTLOG 연동 후보 (BYO 커넥터 원칙 — 회사별 자사 웍스 자격증명 등록)
| # | 연동 | 방식 | 적합도 |
|---|---|---|---|
| A | 알림 채널 | Bot API로 섭외·결재·지급 알림 발송 | 높음 |
| B | SSO 로그인 | 직원이 웍스 계정으로 CASTLOG 로그인(tenant_id는 JWT app_metadata 매핑, Hard NO 1) | 높음 |
| C | 조직도·직급 동기화 | Directory API → 결재라인·`positions` 자동화 | 높음 |
| D | 백업 목적지 | Drive API로 백업 사본 저장(3.2의 목적지 ④) | 중간 |
| E | 미니앱 임베드 | WOFF로 CASTLOG 핵심 화면을 웍스 내부에서 실행 | 중간 |

- 구현 격리: `lib/integrations/`, 자격증명 암호화 저장(`tenant_works_configs`, SMS 패턴).
- 발송은 발송 유형 분리(업무/광고)·로그 기록 규칙 준수.

### 5.3 주의 — 웍스 자체 전자결재와 중복
- 네이버웍스에 자체 결재 기능이 있어 CASTLOG approvals 모듈과 겹칠 수 있음.
- 방침(권장): CASTLOG 결재를 사용하고 웍스는 알림·SSO·조직도·Drive로 보조.
  일부 고객이 웍스 결재를 쓰면 모듈 조합(CLAUDE.md 1-2)으로 수용.

## 6. 향후 과제 (기록)
1. **회사 DB 직접 적재(목적지 ②)** — C+ 2~3단계에서 어댑터로 구현.
2. **B안(회사별 전용 DB 운영)** — 강한 규제 요구 발생 시 최상위 유료 옵션 재검토.
3. **네이버웍스 공식 문서 재확인** — WOFF/SSO/Bot/Directory/Drive 스코프·에디션·국내 제공.
4. **C+ MVP 단계화** — "단계 20: 테넌트 데이터 반출(백업)"로 태스크화.
