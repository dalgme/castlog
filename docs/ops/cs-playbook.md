# 고객 CS·기술대응 플레이북 — "거부는 오류가 아니다"

작성일: 2026-08-22 · 계기: 렛츠 프로젝트 개설 건
관련: CLAUDE.md §12-9(실패 문구 표준) · §14-7(더미 금지) · lib/ux/action-errors.ts

## 0. 왜 이 문서가 있나

렛츠 사고의 실체는 결함이 아니라 **설명 부재**였다. 프로젝트 생성이 권한
규칙에 따라 거부됐을 뿐인데 화면에는 "실패했습니다"만 떴고, 사용자는 규칙과
결함을 구분할 방법이 없으므로 "처음부터 에러 나는 플랫폼"이라고 판단했다.

만약 그 자리에서 **"등급이 이사로 변경된 지 얼마 되지 않아 아직 반영
전입니다. 다시 로그인하면 바로 됩니다"** 라고 말했다면, 사용자는 "아, 오류가
아니라 규칙이구나. 불편하면 바꿔 달라고 하면 되겠네"라고 반응했을 것이다.

**신뢰는 기능이 아니라 거부의 설명에서 깎인다.** 플랫폼이 커질수록 규칙은
늘어나고, 규칙이 늘어날수록 '설명 없는 거부'는 '결함처럼 보이는 순간'을
기하급수로 만든다. 이 문서는 그것을 막는 표준이다.

## 1. 실패의 3분류 — 모든 실패 문구는 이 중 하나로 말한다

| 분류 | 정의 | 문구가 반드시 담을 것 | 예 |
|---|---|---|---|
| ① 규칙 거부 | 회사·플랫폼이 정한 권한/정책에 따른 정상 거부 | **"오류가 아닙니다"** + 어떤 규칙인지 + 지금 할 일 + **규칙 개선 요청 경로(챗봇)** | "지급 화면은 대표·이사 또는 '지급·정산' 위임자만 엽니다" |
| ② 상태 미충족 | 조건이 아직 안 갖춰짐 — 기다리거나 한 단계 먼저 하면 됨 | 무엇이 미충족인지 + **언제/어떻게 충족되는지** | "권한단계가 이사로 변경된 지 얼마 되지 않아 아직 반영 전입니다. 다시 로그인하면 적용됩니다" |
| ③ 시스템 결함 | 우리가 고칠 일 | 인정 + 사용자가 할 수 있는 일(재시도/챗봇 신고) + 내부용 원인 단서 | "서버 데이터베이스가 최신 버전이 아닙니다(마이그레이션 미적용). 캐스트로그에 알려 주세요" |

**금지**: "실패했습니다" 단독 반환. 원인을 모르면 ③으로 분류하고 원문
단서를 덧붙인다 — 모른다고 숨기면 사용자도 우리도 영영 모른다.

## 2. 구현 표준 (개발 규칙 — CLAUDE.md §12-9)

1. **모든 서버 액션의 `ok:false`는 3분류 중 하나로 말한다.** 원인 + 다음 행동.
2. **RLS·권한 거부는 `lib/ux/action-errors.ts explainActionError` 경유.**
   - 권한 변경 반영 시차(토큰 클레임 ↔ 인증 서버 최신값 불일치)를 자동
     감지해 ②로 말한다: "OO에서 XX로 변경된 지 얼마 되지 않아…"
   - 그 외 RLS 거부는 ①로: "오류가 아니라 회사의 권한 규칙" + 챗봇 안내.
3. **DB 스키마 오류(컬럼 없음)는 `describeDbError`가 ③으로 번역** —
   "마이그레이션 미적용"이 화면에 그대로 보인다. 운영 조치 대상이 즉시 드러난다.
4. **눌러도 안 되는 것은 보여 주지 않는다** (§14-7). 권한 없는 버튼은 숨기거나
   비활성 + 이유 표기. 서버 거부에만 의존하는 UI 금지.
5. **새 마이그레이션 컬럼을 참조하는 코드는** (a) 컬럼 부재 폴백을 넣거나
   (b) "마이그레이션 선행 필수"를 PR에 명시하고 미적용 시 ③ 문구가 뜨는지
   확인한다. 현행 기능이 신규 마이그레이션의 인질이 되면 안 된다.
6. **규칙을 새로 만들면 그 규칙의 거부 문구를 같은 PR에서 작성한다.**
   규칙 먼저, 설명 나중은 없다.

## 3. CS 파이프라인 — 문의가 들어오면

```
사용자 막힘
  │
  ├─ 화면 문구가 3분류로 설명  ←  1차 방어선 (대부분 여기서 끝)
  │
  ├─ 챗봇 (화면 우하단)        ←  2차: 규칙 설명 + 우회로 안내
  │    · 프롬프트가 "거부=규칙일 가능성 먼저 설명" (v1.2.0)
  │    · 불편·오류·개선 의견은 자동 분류(suggestion/bug/confusion)되어
  │      help_feedback에 적재
  │
  └─ 관리모드 > 챗봇상담게시판  ←  3차: 캐스트로그가 판정
       · 건의/요청 탭 + FAQ 탭 + '막힌 화면 순위'
```

**게시판 판정 3갈래** (주간 1회 이상 순회):

| 판정 | 뜻 | 조치 |
|---|---|---|
| 설명 부족 | 규칙은 맞는데 문구가 못 알려줌 | 해당 화면 문구를 3분류 표준으로 수정 (당일~수일) |
| 규칙 문제 | 규칙 자체가 업무와 안 맞음 | 기획 판정 → 규칙 변경 또는 유지 사유 회신 |
| 결함 | 진짜 버그 | 수정 + 같은 유형 전수 점검(검수 에이전트) |

같은 화면에서 confusion이 반복되면 그 화면이 문제다 — '막힌 화면 순위'가
그 신호다.

## 4. 기술대응 — 원인을 즉시 좁히는 도구

- **화면 문구 자체가 1차 진단이다**: "마이그레이션 미적용"(③) / "권한
  규칙"(①) / "변경 반영 전"(②)이 그대로 보이므로, 스크린샷 한 장으로
  분류가 끝난다.
- **감사로그**: 관리모드/기업관리에서 시간·행위자별 추적. 권한 변경
  (`user.grade_change`)과 실패 시점을 대조하면 ② 시나리오가 확정된다.
- **원격 검수**: 큰 병합 전 서브에이전트 검수(기본 경로 / DB 정합 / 미완성
  잔재 / 신규 테넌트 재현)를 돌린다 — 렛츠 건에서 실효가 확인된 절차.

## 5. 대형 병합 전 체크리스트

- [ ] 새 마이그레이션의 컬럼·함수·정책을 참조하는 코드 전수 → 폴백 or 선행 명시
- [ ] 새 규칙(권한·게이트)마다 거부 문구가 3분류 표준인가
- [ ] 새 버튼·링크가 권한 없는 사람에게 보이지 않는가 (§14-7)
- [ ] INSERT…RETURNING을 쓰는 곳의 SELECT 정책이 INSERT 정책보다 좁지 않은가
- [ ] 신규 테넌트(데이터 0) + 최하 권한 계정으로 첫날 경로 통과
- [ ] 검수 에이전트 4축 (기본 경로 / DB 정합 / 잔재 / 신규 테넌트 재현)
