# 릴리스 플레이북 — develop 브랜치 + "SQL 먼저" 규칙

작성일: 2026-08-22 · 계기: SMS mode 컬럼 사고 (코드 배포됨 + SQL 미적용)
관련: docs/ops/cs-playbook.md(§5 병합 전 체크리스트) · CLAUDE.md §14-8

## 0. 무엇이 문제였고, 무엇으로 막나

실사용 고객이 생긴 뒤로 main 병합 = 즉시 프로덕션 배포다. 그런데 이
프로젝트에서 **코드(Vercel 자동 배포)와 SQL(운영자 수동 실행)은 서로 다른
배포 경로**라서, 코드만 나가고 SQL이 늦으면 사용 중인 고객이 오류를 맞는다
— SMS 설정 저장 사고가 정확히 이것이었다.

해법은 두 겹이고, **둘 다** 필요하다:

1. **develop 브랜치 분리** — 개발 중 코드가 프로덕션에 흘러들지 않게.
   (이것만으로는 부족하다 — 릴리스 순간의 SQL·코드 순서 문제는 그대로다)
2. **"SQL 먼저" 규칙** — 릴리스 병합 **전에** 마이그레이션을 실행한다.
   마이그레이션을 추가 전용(additive)으로 쓰는 한, 새 컬럼·테이블·함수는
   구버전 코드에 아무 영향이 없으므로 SQL을 먼저 실행해도 안전하다.
   반대로 코드를 먼저 내보내면 새 코드가 없는 컬럼을 참조하다 죽는다.
   **순서에 안전한 방향은 하나뿐이다: SQL → 코드.**

## 1. 브랜치 모델

```
main     ── 프로덕션. Vercel이 자동 배포. 릴리스와 핫픽스만 닿는다.
develop  ── 통합 브랜치. 일상 작업 PR은 전부 여기로.
             Vercel이 브랜치 프리뷰 URL을 자동 생성 → 스테이징으로 사용.
작업 브랜치 ── develop에서 분기, PR → develop.
```

- **일상 개발**: 작업 브랜치 → PR → **develop** 병합. main은 건드리지 않는다.
- **검증**: develop의 Vercel 프리뷰 URL에서 실동작 확인. 마이그레이션이 딸린
  기능은 프리뷰 환경으론 DB 검증이 안 되므로(같은 프로덕션 DB를 보는 구조)
  "미적용 상태에서도 죽지 않는가"를 코드 폴백/선행 조건으로 확인한다.
- **릴리스**: 아래 §2 절차로 develop → main.
- **핫픽스(예외)**: 사용 중 고객이 지금 겪는 오류의 수정은 develop을 기다리지
  않는다. main 직행 PR로 즉시 배포하고, main → develop 역병합으로 동기화한다.
  렛츠 비밀번호 링크 사고 같은 건이 여기 해당한다 — 배치 릴리스가 긴급 수리를
  늦추면 그게 더 큰 사고다.

## 2. 릴리스 절차 (develop → main)

버전 번호: `v1.N` (기능 릴리스마다 N 증가). 주기는 **작게, 자주** — 2주치를
몰아서 내보내면 릴리스당 위험이 커진다. 주 1회 내외를 권장한다.

1. **릴리스 PR 생성**: develop → main. 제목 `릴리스 v1.N`.
2. **PR 본문에 릴리스 체크리스트** (아래 템플릿) 작성 — 특히 마이그레이션
   목록은 파일명을 실행 순서대로 전부 나열한다.
3. **⚠️ 마이그레이션을 먼저 실행한다** (Supabase SQL Editor, 나열 순서대로).
   추가 전용이므로 실행 즉시 프로덕션(구버전 코드)에는 아무 변화가 없다.
4. 필요한 **환경변수**를 Vercel에 넣는다 (역시 코드보다 먼저 넣어도 무해).
5. **병합** → Vercel이 새 코드를 배포. 이 시점에 코드와 스키마가 함께 있다.
6. git **태그** `v1.N` + `docs/releases/v1.N.md`에 릴리스 노트(고객 공지용
   문구 포함) 기록.
7. 배포 후 스모크: 로그인 → 프로젝트 생성 → SMS 테스트 발송 → 관리모드
   연동 점검 화면.

### 릴리스 PR 체크리스트 템플릿

```markdown
## 릴리스 v1.N

### ⚠️ 병합 전 실행 (순서대로)
- [ ] 마이그레이션: 2026XXXXXXXXXX_aaa.sql
- [ ] 마이그레이션: 2026XXXXXXXXXX_bbb.sql
- [ ] 환경변수: XXX (Vercel, 값 출처: …)

### 포함 변경
- (기능/수정 요약 — 고객 공지에 쓸 문장으로)

### 병합 전 확인 (cs-playbook §5)
- [ ] 새 마이그레이션 참조 코드: 폴백 있음 or 위 선행 실행으로 충족
- [ ] 새 규칙의 거부 문구가 3분류 표준인가
- [ ] 신규 테넌트(데이터 0) + 최하 권한 계정 첫날 경로 통과
- [ ] 검수 에이전트 4축 (대형 릴리스일 때)

### 병합 후
- [ ] 태그 v1.N + docs/releases/v1.N.md
- [ ] 스모크 통과
- [ ] (사용자 영향이 있으면) 고객 공지
```

## 3. 마이그레이션 작성 규칙 — "SQL 먼저"가 항상 안전하려면

- **추가 전용(additive)**: 새 컬럼은 `default` 또는 nullable로, 새 제약은
  기존 데이터가 통과하는 형태로. 릴리스 시점에 컬럼 삭제·이름 변경·타입
  축소를 하지 않는다.
- **파괴적 변경은 두 릴리스로 쪼갠다** (expand → contract):
  v1.N에서 새 구조 추가 + 코드가 새 구조 사용, v1.N+1에서 옛 구조 제거.
- **멱등**: `if not exists` / `drop ... if exists` — 두 번 실행해도 같은 결과.
- 그럼에도 코드에는 가능한 한 **컬럼 부재 폴백**(isMissingColumnError)을
  둔다 — 규칙이 지켜지지 않은 날의 마지막 안전망이다.

## 4. 고객 공지

- 릴리스 노트(docs/releases/v1.N.md)에 **고객 언어로 쓴 변경 요약**을 함께
  둔다 — "무엇이 좋아졌나 / 달라진 화면 / 해야 할 일(있다면)".
- 사용자 행동이 바뀌는 릴리스(화면 이동·권한 규칙 변경)는 배포 전 공지가
  원칙. 채널: 현재는 대표 이메일, 추후 앱 내 '새 소식'(백로그).
- 점검이 필요한 큰 릴리스는 야간(21시 이후) 배포 — 광고 문자 차단 시간대라
  발송 영향도 최소다.

## 5. 지금 상태와의 연결

- 이 문서 병합 직후 `develop` 브랜치를 main에서 분기해 푸시한다.
- 미적용 마이그레이션 3건(20260819000006 / 20260820000001 / 20260821000001)은
  **다음 릴리스를 기다리지 않고 지금 실행한다** — 이미 배포된 코드가 기다리는
  SQL이므로 "SQL 먼저" 규칙의 소급 적용이다. (20260820000002는 b안 보류로
  선택 사항.)
