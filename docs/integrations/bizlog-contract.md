# 캐스트로그 ↔ 비즈로그 연동 계약

작성일: 2026-09-09
관련: CLAUDE.md §3(멀티테넌시) · §5(민감정보) · §11-9(service_role 금지) · §15(BYO 커넥터)
대응: docs/handoff/bizlog/ (비즈로그 쪽 설계 초안)

비즈로그는 이용회사가 **자기 PC에 두고 쓰는 회계·경영관리 프로그램**이다.
캐스트로그는 그 존재를 전제하지 않는다 — 비즈로그가 없는 테넌트도 모든 기능이
그대로 동작해야 한다. 이 문서는 API를 제공하는 쪽(캐스트로그)이 갖는 **정본**이며,
비즈로그 레포는 이 문서를 복사해 참조한다.

## 1. 원칙 (변경하려면 이 문서를 먼저 고친다)

1. **필드마다 원천은 하나.** 원천이 아닌 쪽은 그 필드를 고치지 않는다.
   금액이 틀리면 원천에서 고치고 다시 당긴다.
2. **로컬이 항상 클라이언트다.** 두 방향 모두 비즈로그가 요청을 시작한다.
   캐스트로그는 회사 방화벽 안으로 들어가지 않는다.
3. **비즈로그 → 캐스트로그 방향은 보강이지 필수 경로가 아니다.**
   비즈로그가 자동으로 채우는 값은 전부 사람이 손으로도 채울 수 있어야 한다.
4. **주민등록번호·계좌 전체번호는 어떤 방향으로도 흐르지 않는다.** (§5)
   지급명세서 파일은 캐스트로그가 생성하고, 비즈로그는 그 파일을 저장하지 않는다.
5. **`service_role` 키는 로컬 PC에 두지 않는다.** (§11-9)
   연동은 테넌트 한정·스코프 제한·회수 가능한 별도 토큰으로만 한다 (2단계).
6. **당김은 멱등이다.** 같은 데이터를 두 번 받아도 중복이 생기지 않도록
   캐스트로그 ID를 유니크 키로 쓴다.
7. **양쪽 모두 로그를 남긴다.** 캐스트로그는 누가 발급한 토큰이 언제 몇 건을
   가져갔는지(audit_logs), 비즈로그는 언제 무엇을 들여왔는지.

## 2. 필드별 원천

| 데이터 | 원천 | 비즈로그에서 | 캐스트로그에서 |
|---|---|---|---|
| 프로젝트 (ID·코드·이름·발주처·기간) | 캐스트로그 | 미러(읽기) | 원천 |
| 세션·활용 내역 | 캐스트로그 | 미러 | 원천 |
| 전문가 신원 (ID·성명·소득유형) | 캐스트로그 | 미러 | 원천 |
| 지급 확정 금액·원천세·실지급액 | 캐스트로그 | 미러 | 원천 |
| 지급 상태 `confirmed` | 캐스트로그 | 읽기 | 원천 (결재·확정) |
| 지급 상태 `paid` · `paid_at` | **비즈로그** (있을 때) | 원천 — 이체 완료 시 밀어 올림 | 손으로도 찍을 수 있음 |
| 실제 이체 사실 (이체일·거래번호·수수료) | **비즈로그** | 원천 | 없음 |
| 계정과목·분개·전표 | **비즈로그** | 원천 | 없음 |
| 직원 인사 (입퇴사·직급·급여) | **비즈로그** | 원천 | users는 로그인 계정일 뿐 |
| 직원 재직 상태 | **비즈로그** (있을 때) | 원천 — 퇴사 시 밀어 올림 | 계정 비활성화는 손으로도 가능 |
| 직원 주민번호 | 비즈로그 (암호화) | 보유 | **없음** |
| 전문가 주민번호 | 캐스트로그 (분할·래핑, §5) | **보유 안 함** | 지급명세서 생성 시점만 |
| 급여·법인카드·자금계획·경영지표 | 비즈로그 | 원천 | 없음 |

## 3. 방향 A — 캐스트로그 → 비즈로그 (지급 확정 내역)

### 3-1. 1단계 (현재 제공): 엑셀 내보내기 '연동' 시트

경로: `/{tenantSlug}/payments/export` (지급 권한자, experts 모듈)
시트: `연동` — **확정(confirmed)·지급 완료(paid) 건만.** 작성 중·결재 중 건은 넣지 않는다
(확정 전 금액이 장부에 들어가면 되돌리기가 번거롭다).

| 칼럼 | 타입 | 의미 | 비즈로그 키 |
|---|---|---|---|
| 지급ID | uuid | `expert_payment_items.id` | **유니크 키** (`cl_payments.castlog_item_id`) |
| 지급건ID | uuid | `expert_payment_batches.id` | 배치 묶음 |
| 섭외ID | uuid | `expert_engagements.id` | 세션·활용 내역 연결 |
| 프로젝트ID | uuid | `projects.id` | `cl_projects` 키 |
| 프로젝트코드 | text | `projects.code` (비어 있을 수 있음) | 표시용 |
| 프로젝트명 | text | | 표시용 |
| 전문가ID | uuid | `experts.id` — **사람의 안정적 키.** 코드넘버는 프로젝트 안의 자리이지 사람이 아니다 | `cl_experts` 키 |
| 전문가명 | text | | 표시용 — 매칭에 쓰지 않는다 |
| 소득유형코드 | enum | `business_income` / `other_income` / `business` | 세목 판정 |
| 소득유형 | text | 한글 표기 | 표시용 |
| 총비용(원) | int | 계약금액 | |
| 소득세(원) | int? | 스냅샷과 일치할 때만 채움 (아래 주의) | |
| 지방소득세(원) | int? | 위와 같음 | |
| 원천징수(원) | int | 스냅샷 합계 — **참고 계산**, 세액 확정은 세무 검토 | |
| 실지급(원) | int | 총비용 − 원천징수 | |
| 상태코드 | enum | `confirmed` / `paid` | |
| 확정일시 | ISO | `confirmed_at` | 증분 당김 기준 |
| 지급일시 | ISO? | `paid_at` | |

**소득세·지방소득세 분리 주의.** 스냅샷은 합계만 저장한다. 내보낼 때 현재 세율로
다시 나눠 보고 합계가 스냅샷과 같을 때만 채운다. 세율이 바뀐 뒤 옛 건을 내보내면
빈 칸이 될 수 있으며, 그때는 비즈로그가 합계만 쓰고 분리는 회계 담당자가 한다.

### 3-2. 2단계 (미구현): 읽기 전용 연동 API + 연동 토큰

1단계에서 실제로 쓰이는 칼럼이 확정된 뒤에 만든다. 설계 요지만 적어 둔다.

- 토큰: `tenant_integration_tokens` — 테넌트 한정, 대표(또는 settings 위임자)가
  발급·회수, 만료일 필수, 해시만 저장, 스코프 목록.
- 스코프는 위험도가 갈리는 지점에서 자른다 (§3-1 위임 스코프와 같은 원칙):
  `payments:read` · `payments:mark_paid` · `projects:read` · `staff:deactivate`
  — 읽기와 쓰기는 별개 스코프, 쓰기 스코프는 비즈로그가 원천인 필드 하나씩.
- 조회: `GET /api/integrations/payments?since=<확정일시 커서>` — 커서 기반 증분.
  응답 필드는 3-1과 동일. 1요청 상한·시간당 상한.
- 인증은 JWT가 아니므로 RLS 우회가 필요하다 → **`service_role`이 아니라**
  토큰 검증 후 `app.tenant_id()`를 그 테넌트로 고정한 전용 DB 역할로 실행.
  구현 전 docs/decisions/에 판정을 남긴다 — 새 인증 축이다.

### 3-3. 3단계 (미구현): 확정 이벤트 알림

지급 확정 시 비즈로그가 알아채도록. 2단계가 실제로 쓰이는 게 확인된 뒤에.

## 4. 방향 B — 비즈로그 → 캐스트로그 (보강)

2단계 토큰이 생긴 뒤에만 가능하다. 지금은 사람이 손으로 한다.

| 이벤트 | 비즈로그가 보냄 | 캐스트로그 동작 | 손으로 하는 현재 경로 |
|---|---|---|---|
| 이체 완료 | 지급건ID + 이체일 | 배치 `paid`, `paid_at` 기록, 전문가 지급 완료 알림 | 지급 화면 '지급 완료' 버튼 |
| 직원 퇴사 | 직원 이메일(또는 users.id) + 퇴사일 | 계정 비활성화 (grade·role 유지, 로그인만 차단) | 설정 > 임직원 |

규칙: 캐스트로그는 받은 값을 **검증**하고(그 배치가 `confirmed`인가, 그 직원이 이
테넌트 소속인가) 아니면 거부한다. 비즈로그가 보낸 값이라고 그대로 믿지 않는다.

## 5. 충돌 규칙

- 비즈로그의 `cl_*` 미러는 재당김 시 캐스트로그 값으로 **덮어쓴다.** 로컬 수정본을
  보존하지 않는다.
- 이미 전표가 끊긴 건은 예외: 비즈로그가 전표 시점의 값을 스냅샷으로 고정하고,
  이후 원천이 바뀌면 덮어쓰지 않고 **차이를 화면에 띄운다.** 회계 담당자가 수정
  전표로 처리한다. (`cl_payments.synced_at` · `source_confirmed_at` 비교)
- 캐스트로그는 `confirmed` 이후 금액을 바꾸지 않는다 (지급 확정본 동결). 바꿔야
  하면 취소 후 새 배치 — 새 지급ID가 나오므로 비즈로그는 취소 건을 별도로 알 수
  있어야 한다 → 2단계 API 응답에 `canceled` 상태 포함 예정.

## 6. 하지 않는 것

- 주민번호·계좌 전체번호를 실어 보내는 칼럼·엔드포인트
- 비즈로그가 캐스트로그 원천 필드를 UPDATE 하는 경로
- 캐스트로그 기능이 비즈로그 응답을 기다리는 구조
- 회사별 커넥터를 캐스트로그가 만들어 주는 것 — 표준 API만 제공, 커넥터는
  각 회사가 만든다 (§15 네이버웍스 연동과 같은 BYO 축)
